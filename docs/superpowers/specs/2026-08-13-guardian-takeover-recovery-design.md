# 豆包守护接管恢复设计

## 问题

普通豆包启动后，守护能够识别并关闭它；但关闭之后，只要路径解析、启动或 5 秒 CDP 端口确认任一步失败，下一轮探测会把豆包判定为 `stopped`。现有被动模式对 `stopped` 只等待用户再次启动，因此豆包永久停在已关闭状态。

## 目标

当“自动保持皮肤”开启、“关闭豆包前询问我”关闭、“暂时停用皮肤”关闭时，普通豆包一旦被守护接管，守护必须完成整个闭环：关闭普通豆包、以 9225 皮肤模式重启、等待 CDP、注入保存主题。首次重启失败不得退出接管或退回普通被动等待。

## 设计

`SkinGuardian` 增加内存态 `takeoverPending`：

1. 探测到 `restart-required` 且允许自动重启时，将 `takeoverPending` 设为 true。
2. 调用重启依赖；成功或失败都保持接管上下文，直到连接并成功应用主题。
3. 接管期间若探测为 `stopped`，使用 `active-skin.json` 中的 `doubaoExecutable` 与 `port` 直接启动豆包，而不是返回 `waiting-for-doubao`。
4. 启动调用抛错时转换为 `retry`，继续指数退避；不得让 `tick()` Promise rejection 终止守护循环。
5. 探测到 `connected` 并完成 `applied`/`partial` 后清除 `takeoverPending`。
6. `stop()`、状态被删除或暂时停用时清除 `takeoverPending`，不得重新启动豆包。

`ApplicationRuntime` 的守护依赖使用 `ActiveSkinState.doubaoExecutable` 作为接管恢复的首选准确路径；设置路径只作为初次发现/用户选择来源。

## 安全边界

- 只有已经进入自动接管流程后，`stopped` 才允许主动启动豆包。
- 用户主动关闭豆包且未发生普通模式接管时，继续保持现有被动等待，不自动拉起。
- “关闭豆包前询问我”开启时，不进入自动接管。
- “暂时停用皮肤”立即停止守护与接管恢复。
- 不新增设置、依赖或 UI。

## 错误处理

- 关闭失败：保留接管状态并按退避重试，不启动第二个豆包。
- 启动抛错、路径短暂不可用、CDP 超时：记录隐私安全阶段状态并重试。
- 主题注入失败：保留接管状态并重试；只有 `applied`/`partial` 清除。

## 测试

1. 普通豆包接管成功：`restart-required` 后进入 pending，随后 connected 并应用主题。
2. 关闭成功但首次 CDP 确认失败，随后探测 stopped：使用 state 精确路径再次启动。
3. 接管期间 launch 抛错：守护继续安排下一次 retry。
4. 非接管 stopped：仍只等待，不自动启动。
5. stop/暂时停用发生于重试期间：不得继续 launch/apply。
6. 状态路径优先于 settings/default 路径。

## 验收

任务管理器结束全部豆包进程后，打开普通豆包；守护关闭普通豆包后，即使第一次重启确认失败，也会继续自动恢复，最终出现带上次皮肤的豆包。后台守护不退出，且用户主动关闭豆包不会被无条件拉起。
