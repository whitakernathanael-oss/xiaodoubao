# 单一主导色壁纸主题与半透明侧栏设计

日期：2026-08-10

## 目标

修正“壁纸自动提取主题色”把差异很大的多个原始颜色同时用于 UI，导致界面混色、发灰或色彩割裂的问题。壁纸只负责提供一个种子色；界面的背景、表面、边框、文字、按钮和状态色全部由该种子色派生。

同时把豆包左侧栏调整为能透出壁纸的同色系玻璃效果，接近参考图 `E:\studio-custom-look.png`，但不牺牲文字可读性。

## 范围

本次保留现有图片缩放、像素采样和 RGB 量化入口，不引入 Material Color Utilities，也不推倒主题结构重写。MVP 使用现有 TypeScript 与 HSL 运算完成：

- 聚合 5–8 个候选色族；
- 选择唯一 `dominantColor` / `seedColor`；
- 检测相互竞争的不同色系；
- 从单一种子色生成完整同色系 palette；
- 让预览和真实豆包侧栏使用半透明同色系表面；
- 增加算法与注入样式测试。

不在本次范围：用户手工调色、完整 HCT/OKLCH 重构、从壁纸同时生成双主题、让原始第二候选色参与大面积表面配色。

## 当前问题

现有算法对 3-bit/channel RGB 色桶按 `count * (0.5 + saturation)` 排序，直接选第一个色桶作为主色，并另选一个色相不同的高饱和颜色作为强调色。界面表面色又来自整张图片的 RGB 平均值。

这会产生三个问题：

1. 同一色系的渐变会分散到多个 RGB 色桶，面积权重被低估；
2. 小面积高饱和颜色可能因饱和度加成抢走主导权；
3. 蓝色和黄色等冲突色被分别用于 accent 与 surface，或经 RGB 平均得到与原图观感无关的灰、绿、脏色。

此外，当前壁纸层优先挂在聊天区，侧栏本身使用不透明底色，因此即使降低侧栏色值亮度，也不会出现参考图中的“壁纸透过玻璃”效果。

## 方案

### 1. 保留量化，增加色族聚合

继续使用现有缩图采样和 RGB 量化。量化后把相近的色桶转换到 HSL，根据环形色相距离和明度差聚合为色族，最多保留 8 个候选色族。

色族的代表色只由该色族内部像素加权得到；不同色族之间禁止 RGB 平均。面积、饱和度、明度和空间连续性均按色族统计，因此深蓝与浅蓝可以被识别为同一个蓝色色系，而蓝色与黄色保持为两个竞争候选。

### 2. 候选过滤

在评分前过滤不适合作为彩色 UI 种子的候选：

- 接近纯白或纯黑；
- 饱和度很低的灰色；
- 明度处于极端区间；
- 有效面积过小且没有连续区域。

过滤只决定彩色种子候选。若整张图片主要由黑白灰组成，则进入 neutral fallback，而不是强行寻找高饱和小物体。

### 3. 唯一主导色评分

每个候选色族计算以下归一化分量：

- `areaWeight`：候选像素数 / 有效采样像素数；
- `saturationScore`：中等到较高饱和度得分较高，但过饱和不继续无限加分；
- `uiUsabilityScore`：综合明度是否远离极端、是否接近灰色、饱和度是否适合作为 UI 种子；
- `spatialContinuityScore`：候选最大连续区域或同色邻接比例，避免零散小物体得高分。

最终评分固定为：

```text
score =
  areaWeight * 0.55
  + saturationScore * 0.20
  + uiUsabilityScore * 0.15
  + spatialContinuityScore * 0.10
```

面积拥有最高权重。单个高饱和红色小物体不能只靠饱和度超过大面积背景。

### 4. 色相冲突和双主色竞争

候选色使用 HSL 色相并计算环形距离：

```text
hueDistance = min(abs(h1 - h2), 360 - abs(h1 - h2))
```

当第一、第二候选的 `hueDistance >= 90°` 时，认定为不同色系。无论分数差多少，第二候选都不能参与 background、surface、secondary 等核心颜色生成。

若同时满足：

- 两者相对分数差小于 15%；
- `hueDistance > 90°`；

则进入“双主色竞争”决策，严格按以下顺序确定唯一种子色：

1. 面积更大；
2. 最大连续区域更大；
3. UI 可用性更高；
4. 饱和度不过高、更适合大面积界面。

最终始终只输出一个 `seedColor`。不随机选择，也不把两种颜色做 RGB 平均。

### 5. 单一种子色生成 UI palette

MVP 使用 HSL 固定种子色相，通过调整 saturation 与 lightness 生成同色系色阶。输出或内部生成的角色包括：

- `primary`
- `primaryHover`
- `secondary`
- `surface`
- `surfaceVariant`
- `background`
- `border`
- `text`
- `muted`
- `accent`

浅色与深色路线由壁纸总体亮度、种子色可用性和对比度共同决定。黄色等高明度种子必须先适当降饱和、调整 tone，再生成表面色和文字色。

第二候选色在 MVP 中不直接用作 accent。即便它与主色区别明显，也先从种子色本身派生 accent，从根源上避免双主题回归。未来若开放原图 accent，也必须满足小面积、对比度合格、只用于小控件且不参与大面积表面的全部条件。

黑白灰壁纸进入 neutral fallback：使用稳定的中性灰 palette，只允许极低色度，不从小面积彩色噪点生成高饱和主题。

### 6. 半透明侧栏

真实注入时，壁纸层挂到应用根容器，覆盖聊天区和侧栏的共同背景。侧栏使用由 `seedColor` 派生的半透明 surface：

- 约 70%–74% 的同色系底色；
- 保留适度 `backdrop-filter: blur(...)`；
- 普通项目透明，hover/selected 使用同色系浅层叠加；
- 边框与文字从 tonal palette 获取，满足浅/深模式对比度；
- 输入框和弹层仍可使用更高不透明度，避免壁纸细节干扰阅读。

本地预览与真实注入使用同一主题变量语义，避免预览透明、真实界面仍不透明。

## 数据流

```text
上传壁纸
→ 缩图与采样
→ 现有 RGB 量化
→ HSL 色族聚合（最多 8 个）
→ 过滤白/黑/低饱和灰/极端亮度
→ 候选评分
→ 色相冲突与双主色竞争判断
→ 唯一 seedColor
→ HSL tonal palette
→ 预览主题变量
→ 保存并注入豆包
```

## 错误与回退

- 图片无法解码：保持当前主题不变并显示操作失败，不写入半成品 palette；
- 有效彩色候选为空：使用 neutral fallback；
- 采样尺寸信息缺失：空间连续性按可用邻接数据计算，不能计算时取保守值，不阻断取色；
- 派生色对比度不足：优先调整 tone，再选择黑/白文字，不改变种子色系；
- 豆包 DOM 适配器只识别部分区域：已识别区域使用新 palette，状态继续显示“部分兼容”。

## 测试与验收

算法测试必须覆盖：

1. 蓝色 55% + 黄色 40%：唯一种子为蓝色；
2. 黄色 55% + 蓝色 40%：唯一种子为黄色，生成的 UI 黄色降低饱和并调整 tone；
3. 深蓝 + 浅蓝：归入或选择同一个蓝色色系，不触发双主题；
4. 红色 + 橙色：视为相近色系，不强制判为冲突；
5. 蓝色 + 黄色面积接近：触发双主色竞争，按确定性规则只保留一个；
6. 黑白灰壁纸：进入 neutral fallback，不生成高饱和种子；
7. 大面积低/中饱和背景 + 小面积高饱和红色：红色不能抢走主导权。

界面与注入测试必须覆盖：

- palette 中大面积角色全部来自 seedColor 同色系；
- 不存在冲突候选的 RGB 平均；
- 本地预览侧栏使用半透明主题表面；
- 注入 CSS 把壁纸挂到应用根容器，并为侧栏输出透明同色系背景；
- 现有壁纸显示、历史对话骨架屏修复和主题 ZIP 行为不回归。

- `tests/theme-coloring.test.ts`、`tests/preview.test.ts`、`tests/injector.test.ts`：palette 映射、预览与真实注入回归测试。

## 完成标准

- 同一张壁纸永远只产生一个核心 `seedColor`；
- 蓝黄等强冲突色不会共同控制 UI 大面积区域；
- UI 表面色不再由不同色系 RGB 平均产生；
- 七组指定测试全部通过；
- 本地预览和真实豆包侧栏均能透出壁纸，并保持文字可读；
- 全量测试、类型检查与 Windows 打包通过。
